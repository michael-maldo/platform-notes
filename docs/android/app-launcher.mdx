# Application Launch and Shell Initialization


For this walkthrough, assume a **fresh launch**: no existing Activity, retained ViewModel, or restored Fragment. The expected result is an expanded sidebar showing Dashboard, Orders, and Settings, with Dashboard selected and its Fragment displayed.

We’ll distinguish three kinds of execution:

| Marker | Meaning |
|---|---|
| **Framework callback** | Android calls your code, such as `onCreate()`. |
| **Java call** | Ordinary synchronous execution on the current thread. |
| **LiveData notification** | LiveData invokes a registered observer when its lifecycle owner is active. This does **not** inherently mean a background thread. |



## Android identifies the launch Activity
- MainActivity has an intent filter containing MAIN and LAUNCHER, This tells Android which Activity to open when the launcher icon is tapped.
- Unlike a conventional Java application, you do not write a main() method or construct this Activity yourself. Android manages its creation and lifecycle.

## The Activity obtains its ViewModel
A "Retained ViewModel" in Android is a special kind of ViewModel that is designed to survive configuration changes, such as screen
rotations (when the device goes from portrait to landscape)

**ViewModel**
- A ViewModel is a class that holds and manages UI-related data in a lifecycle-conscious way
- It helps you separate the UI logic from the data logic
- ensures that the data persists even if the activity is destroyed and recreated

```
MainViewModel viewModel = new ViewModelProvider(this).get(MainViewModel.class);
```
- `this` is the Activity and establishes the ViewModel’s ownership scope

## The Activity becomes active; LiveData delivers initial values
**Framework callbacks:** Android advances the Activity through `onStart()` and `onResume()`. Your overrides are at [line 338](/home/gnostex/AndroidStudioProjects/StaffPlatform/app/src/main/java/dev/techlabs/staffplatform/MainActivity.java:338) and [line 344](/home/gnostex/AndroidStudioProjects/StaffPlatform/app/src/main/java/dev/techlabs/staffplatform/MainActivity.java:344).

**LiveData notifications:** When the lifecycle reaches `STARTED`, registered observers become active and receive their existing values.

No button click or `setValue()` is needed to trigger this initial delivery.

Each observer then makes ordinary synchronous Java calls:

- Expanded-menu observer → `renderSidebar.run()`.
- Selection observer → `renderSidebar.run()` and Fragment routing.
- Sidebar observer → width calculation and `renderSidebar.run()`.

At [line 283](/home/gnostex/AndroidStudioProjects/StaffPlatform/app/src/main/java/dev/techlabs/staffplatform/MainActivity.java:283), `true` produces a width of `220 × density` pixels. The XML uses dp; Java’s `LayoutParams.width` uses pixels.

You should expect **multiple sidebar renders during startup**, because all three observers render. Do not treat one breakpoint hit as the whole initialization.




## The renderer creates the initial navigation rows
The synchronous call chain is:

```text
renderSidebar.run()
  → SidebarRenderer.render()
    → remove existing rows
    → renderLevel()
      → createRow() for each visible item
      → attach click listener
      → add row to container
```

[SidebarRenderer.java:33](/home/gnostex/AndroidStudioProjects/StaffPlatform/app/src/main/java/dev/techlabs/staffplatform/navigation/SidebarRenderer.java:33) clears the container.

[Line 64](/home/gnostex/AndroidStudioProjects/StaffPlatform/app/src/main/java/dev/techlabs/staffplatform/navigation/SidebarRenderer.java:64) inflates [item_sidebar.xml](/home/gnostex/AndroidStudioProjects/StaffPlatform/app/src/main/res/layout/item_sidebar.xml): an icon and label inside a clickable row.

The renderer reads:

```text

expanded = true
expandedMenus = []
```

At line 82, it calls [NavigationTree.isHighlighted(), line 16](/home/gnostex/AndroidStudioProjects/StaffPlatform/app/src/main/java/dev/techlabs/staffplatform/navigation/NavigationTree.java:16). Dashboard matches exactly, so its row receives the selected styling.

The child-rendering condition at line 54 is false for Orders and Settings because neither ID is in `expandedMenus`. Therefore, only three top-level rows appear.

`FlyoutNavigation` is **not instantiated during launch**. Its path starts only when a collapsed parent is clicked.




## Initial selection schedules the Dashboard Fragment

The selected-navigation observer receives `"dashboard"`.

At [MainActivity.java:148](/home/gnostex/AndroidStudioProjects/StaffPlatform/app/src/main/java/dev/techlabs/staffplatform/MainActivity.java:148), `findFragmentById()` returns `null` on this fresh launch.

The observer then:

1. Constructs `DashboardFragment` at line 158.
2. Creates a transaction at line 182.
3. Targets `mainContent` with `replace()` at line 183.
4. Calls `commit()` at [line 184](/home/gnostex/AndroidStudioProjects/StaffPlatform/app/src/main/java/dev/techlabs/staffplatform/MainActivity.java:184).

**Important execution boundary:** `commit()` schedules the transaction; it does not synchronously create the Fragment’s View before returning.

Later, FragmentManager executes the transaction and invokes the Fragment lifecycle.

**Framework callback:** [DashboardFragment.onCreateView(), line 25](/home/gnostex/AndroidStudioProjects/StaffPlatform/app/src/main/java/dev/techlabs/staffplatform/features/dashboard/DashboardFragment.java:25).

Its synchronous `inflate()` call at line 32 builds [fragment_dashboard.xml](/home/gnostex/AndroidStudioProjects/StaffPlatform/app/src/main/res/layout/fragment_dashboard.xml), containing “Dashboard” and “Welcome to StaffPlatform”.

The `false` argument means the inflater does not attach the View itself; FragmentManager manages that attachment.

Finally, the insets listener registered at [MainActivity.java:330](/home/gnostex/AndroidStudioProjects/StaffPlatform/app/src/main/java/dev/techlabs/staffplatform/MainActivity.java:330) receives framework inset dispatches and applies system-bar padding to `staffShell`. This callback’s timing is separate from registering it.
